# NEXLEVR Intermediate Task 01 — Home SOC Lab (Wazuh)

**Lab date:** October 22, 2026  
**Platform:** Wazuh installed on a fresh Ubuntu Server VM in Oracle VirtualBox  
**Status:** Technical test completed; evidence-image upload and credential rotation pending  
**Environment:** Personal training lab only — no production/customer systems

## Task requirement

> Set up a home SOC lab (Wazuh or Security Onion in a VM), generate test activity, and show the alerts it produced.

## Objective

Install a working SIEM/SOC lab, safely generate authentication failures, review the resulting security alerts, and document a reasoned analyst verdict.

## Lab architecture

```text
Mokka host (Garuda Linux)
  |
  | https://127.0.0.1:8443 (local-only NAT forwarding)
  v
VirtualBox VM: NEXLEVR-Wazuh
  - Ubuntu Server 24.04 LTS (Noble Numbat)
  - Wazuh manager + indexer + dashboard + Filebeat
  - Adapter 1: NAT (guest address observed: 10.0.2.15)
  - NAT port forwarding: host 127.0.0.1:8443 -> guest TCP 443
  - SSH server, with controlled test logins to 127.0.0.1
  - Wazuh reads local authentication events from journald
```

This was a **new VM**, separate from the existing Kali, pfSense, and original Wazuh home labs. No production tenant data was used. The Wazuh overview showed **zero separately registered remote agents**; the alerts shown here came from the local manager/host (`agent.id: 000`, `agent.name: nexlevr-wazuh`). A second test endpoint was not needed to meet this particular task.

## Setup and verification

1. Installed Ubuntu Server 24.04 LTS in the new `NEXLEVR-Wazuh` VirtualBox VM.
2. Left the installer network adapter using DHCP on VirtualBox NAT.
3. Installed the Wazuh all-in-one components with the Wazuh installer.
4. Verified the services:
   ```bash
   sudo systemctl is-active wazuh-manager wazuh-indexer wazuh-dashboard filebeat
   ```
   **Observed result:** four consecutive `active` responses.
5. Configured *local-only* host-to-guest dashboard forwarding, using host port 8443 and guest port 443.
6. Opened and authenticated to the dashboard via `https://127.0.0.1:8443` from the host computer.
7. Confirmed that the **Threat Hunting → Events** interface could display alerts.

> The exact installer version should be checked before claiming a particular installed Wazuh release. The installation used the Wazuh 4.14 installer URL during this exercise.

## Controlled security test

The test was performed **inside the new Ubuntu VM**, against the VM itself:

```bash
sudo systemctl start ssh
sudo systemctl is-active ssh
ssh nexlevr-test@127.0.0.1
```

The deliberately nonexistent user `nexlevr-test` was used, and incorrect passwords were entered repeatedly. No real user account was targeted. Local SSH journal entries were checked with:

```bash
sudo journalctl -u ssh --since "10 minutes ago" --no-pager | tail -n 30
```

The Ubuntu log showed invalid-user and failed-password events from `127.0.0.1`, followed by PAM authentication failures.

## Observed Wazuh alerts

These are the six events visible in the captured search result. They should not be interpreted as six separate attackers or six successful logins.

## Detailed investigation — rule 2502

The opened Wazuh document showed:

| Field | Verified value |
| --- | --- |
| Host / agent | `nexlevr-wazuh` |
| Agent ID | `000` |
| Rule ID | `2502` |
| Rule level | `10` |
| Detection | `syslog: User missed the password more than one time` |
| Decoder | `sshd` |
| Collection location | `journald` |
| ATT&CK tactic | Credential Access |
| ATT&CK technique | `T1110` — Brute Force |
| Wazuh event timestamp | October 22, 2026, 19:52:13 (dashboard display) |
| Test destination | Local VM SSH service |
| Test source | `127.0.0.1` (loopback, as shown in log context) |

The `full_log` described multiple authentication failures. The technique mapping reflects the type of behavior detected; it does **not** establish that a malicious person attacked the server.

## Analyst verdict

**True positive for the intended test condition; benign, authorized lab activity.**

Wazuh correctly raised alerts for repeated failed SSH authentication attempts, including a level 10 event associated with multiple password failures. The source was the local loopback interface, and the activity was intentionally generated by the lab operator. No successful unauthorized login, persistence, lateral movement, or host compromise was demonstrated.

**Limitations:** The test used a single VM and localhost, not a multi-agent or real-world attack scenario. Additional endpoint onboarding, longer retention, alert routing, and varied authentication scenarios were not evaluated here.
